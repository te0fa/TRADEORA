## SECTION 4 — CORE ENGINEERING PRINCIPLES

1. **Extensibility Over Optimization** — Never optimize for short-term implementation. Always design extension points for capabilities not yet conceived. A solution that solves today's problem but prevents tomorrow's evolution is architecturally wrong.

2. **Replaceability** — Every component — AI model, database, cloud provider, message bus, authentication provider — must be replaceable without system redesign. If removing a component requires changing more than 20% of the codebase, the design is wrong.

3. **Abstraction Layers Always** — No direct coupling to vendors, providers, or platforms. Every external dependency sits behind a Port (interface) in the Application layer. Implementations (Adapters) live in the Infrastructure layer.

4. **Event-First Design** — All significant state changes produce events. Events are the system's permanent memory. Events enable time-travel queries, audit trails, AI training, and agent communication.

5. **Domain Purity** — Domain logic never depends on infrastructure, AI providers, or frameworks. Domain objects are pure business objects. They must run and be tested without NestJS, FastAPI, Flutter, or any AI library.

6. **Testability as a Design Constraint** — If a component cannot be tested in isolation, the design is wrong. Testability is not a testing concern — it is an architectural constraint that must be satisfied before implementation.

7. **Observability Built-In** — Every component produces metrics, distributed traces, and structured logs by design. Observability is never an afterthought. Reference: `docs/OBSERVABILITY_ARCHITECTURE.md`.

8. **Security by Design** — Security is a first-class architectural concern. Every design decision must have a security implication analysis. Reference: `docs/SECURITY_ARCHITECTURE.md`.

9. **Gradual Autonomy** — AI systems earn autonomy through demonstrated accuracy and regulatory approval. Start with information display, advance to advisory, earn trust, gain autonomy incrementally. Never leap to automation without proven reliability.

10. **Human Dignity** — Every automated decision must be explainable to a non-technical user, reversible without data loss, and ultimately subject to human override. Financial automation is a privilege earned through trust.

## SECTION 5 — CORE AI PRINCIPLES

1. **AI is an Advisor First** (Phase 1–2) — During Phase 1 and Phase 2, AI provides recommendations. Humans make final decisions. No order is executed, no portfolio is modified without explicit human approval. This is non-negotiable.

2. **AI Provider Independence** — No AI model is indispensable. The platform must function with any provider, or with zero external providers (Ollama local). Current mechanism: LiteLLM proxy. Reference: `docs/AI_RUNTIME_ARCHITECTURE.md § 2`.

3. **Explainability by Default** — Every AI output includes an explanation accessible to a non-technical Arabic-speaking user. No recommendation is delivered without a plain-language rationale, confidence score, and supporting evidence.

4. **Confidence Transparency** — AI confidence levels are always disclosed. Low-confidence outputs are always flagged. Threshold: <0.75 confidence = mandatory human escalation. Reference: `docs/AI_RUNTIME_ARCHITECTURE.md`.

5. **Multi-Model Consensus** — No single AI model is trusted absolutely. The 17-school consensus architecture reduces hallucination risk by requiring agreement across diverse analytical frameworks. Reference: `docs/AI_RUNTIME_ARCHITECTURE.md § Schools`.

6. **Continuous Learning Without Catastrophic Forgetting** — AI models improve continuously without discarding prior learned behaviors. Learning is validated before deployment. Rollback is always possible.

7. **Human-in-the-Loop Escalation** — Low-confidence decisions always escalate to human review. The AI's job is to reduce the human's cognitive load, not to eliminate human judgment.

8. **AI Safety First** — No AI output is actioned without passing a global safety engine. Safety checks include: sanity validation, confidence gating, regulatory compliance, and anomaly detection.

## SECTION 6 — ENTERPRISE PLATFORM PRINCIPLES

1. **Platform Thinking** — Tradeora is a platform that enables third-party intelligence, not a monolithic application. Every capability that can be a plugin should eventually become a plugin.

2. **API-First** — Every capability has an API before it has a UI. The API is the canonical interface. The UI consumes the API like any other client.

3. **Plugin Architecture** — Third-party providers can extend Tradeora's capabilities without modifying core platform code. Plugin contract: OpenAPI spec + Kafka event subscription + permission scope. Reference: `docs/PLUGIN_ARCHITECTURE.md` (Phase 7.18).

4. **Multi-Tenancy Ready** — The architecture must support isolated tenants (family offices, institutions) from Phase 1 design. Tenant isolation: separate schemas, separate encryption keys, separate audit trails.

5. **White-Label Ready** — The core AI engine must be separable from the Tradeora brand for B2B licensing. Core services expose a white-label API.

6. **Regulatory Adaptability** — Compliance rules are configuration, not code. FRA, SEC, MIFID II, SAMA each have different rules — the platform adapts via regulatory adapter plugins.

7. **Enterprise SLA** — Tier-1 operations (EGX trading-critical) must achieve 99.99% availability during EGX session hours (08:45–15:15 Cairo), regardless of scale. Reference: `docs/OBSERVABILITY_ARCHITECTURE.md § SLOs`.

## SECTION 7 — INTELLIGENCE PRINCIPLES

1. **Layered Intelligence** — Raw data → Processed signals → Derived insights → AI recommendations → Autonomous actions. Each layer is gated by a reliability threshold before advancing to the next.

2. **Intelligence Compounds** — Every user interaction improves the system's intelligence for all users, subject to privacy constraints (differential privacy, opt-in consent).

3. **Domain-Specific Models** — General-purpose LLMs are enhanced by domain-specific financial knowledge. Egyptian market knowledge, EGX regulations, FRA rules, and Arabic financial terminology are embedded in model context.

4. **Signal Fusion** — No single data source is sufficient. Truth emerges from fusion of: price data, fundamental analysis, news sentiment, technical indicators, macroeconomic data, and analyst research.

5. **Intelligence Personalization** — The system's intelligence adapts to each user's risk profile, investment horizon, behavioral patterns, and past outcomes. Phase 3+: Experience Graph enables hyper-personalization.

6. **Intelligence Verifiability** — AI intelligence claims must be backtestable against historical data. No school receives trust credit without demonstrated statistical validity.

## SECTION 11 — DECISION INTELLIGENCE PRINCIPLES

### The Autonomy Ladder

```
Level 0: Information Display
  ← Phase 1 market data, prices, charts
  Human decision: 100%

Level 1: AI Advisory with Confidence Scores
  ← Phase 1 current (APPROVED — 17 schools)
  Human decision: 100% (AI advises, human decides)

Level 2: AI-Suggested Orders with Human Approval
  ← Phase 2 target (semi-autonomous, FRA notification)
  Human decision: required for every order
  AI decision: order parameters, timing, sizing suggestion

Level 3: AI-Executed Orders within Pre-Approved Rules
  ← Phase 3 (FRA regulatory approval required)
  Human defines: investment policy, risk limits, position limits
  AI executes: within those approved boundaries
  Human override: always available, instant

Level 4: Autonomous Portfolio Management
  ← Phase 4 (regulatory maturity globally)
  Human defines: long-term goals and absolute risk limits
  AI manages: entire portfolio within approved policy
  Human review: periodic (monthly/quarterly)
```

**CRITICAL**: Autonomy is earned through demonstrated accuracy, not assumed. Each level requires:
1. >N months of demonstrated accuracy at the previous level
2. Explicit regulatory approval from the relevant regulator
3. User opt-in with informed consent disclosure
4. Kill switch: user can revert to previous level instantly
5. Full audit trail of every autonomous action

## SECTION 12 — LEARNING PRINCIPLES

1. **Continuous Learning** — The platform learns from every recommendation outcome, every user interaction, and every market event. Learning is never complete.

2. **Catastrophic Forgetting Prevention** — New learning never erases prior knowledge. Elastic Weight Consolidation (EWC) or similar techniques prevent destructive interference.

3. **A/B Testing of Model Improvements** — Every model change is validated in A/B tests against a holdout population before deployment to all users.

4. **Performance Degradation Detection** — Automated monitoring detects when AI performance degrades below threshold. Degradation triggers automatic rollback to the last validated model state.

5. **User Feedback Integration** — User explicit feedback (thumbs up/down on recommendations) and implicit feedback (did user act on recommendation?) are both learning signals.

6. **Learning Governance** — Every learning cycle is logged, attributable, and reversible. Model changes require validation by the Chief AI Architect before promotion to production.

## SECTION 17 — SECURITY PRINCIPLES

*(Extends `docs/SECURITY_ARCHITECTURE.md` — adds philosophical layer)*

1. **Zero-Trust is Permanent** — Zero-trust is not a Phase 1 compromise. It is the permanent security architecture of Tradeora for all phases.

2. **Financial Data Sovereignty** — User financial data belongs to the user. Tradeora is a custodian, not an owner. Users can export or delete their data at any time.

3. **Right to Forget** — PDPL 2020 (Egyptian) compliance requires the ability to delete all personally identifiable data. The architecture supports soft deletion + anonymization.

4. **Security Evolves with Threats** — Quarterly security architecture review. Annual penetration testing. Continuous CVE monitoring for all dependencies.

5. **AI-Specific Security** — Adversarial input protection: all AI inputs are sanitized. Model inversion attack prevention: models never return training data. Prompt injection prevention: all LLM inputs are validated and sandboxed.

## SECTION 18 — PRIVACY PRINCIPLES

1. **Privacy by Design** — Privacy is a design constraint, not a compliance checklist. Every feature design starts with: "What data does this need? What is the minimum?"

2. **Minimum Data Collection** — Collect only what intelligence requires. Every data collection decision must be justified by a concrete intelligence improvement.

3. **Differential Privacy for Collective Intelligence** — When aggregating user signals for collective intelligence, differential privacy noise is added before any aggregation. Individual patterns cannot be reverse-engineered from collective data.

4. **User Control** — Every data point has a visible purpose. Users can view what data is held about them, request export, and request deletion. This is a UI feature, not a support ticket process.

5. **Federated Learning Consideration** — Phase 3+: explore training models on user devices without centralizing data. Privacy-preserving AI is the long-term architecture direction.

| Learning Agent | Outcome tracking, weight calibration | Celery + PostgreSQL analytics |

3. **Agent Communication** — Agents communicate via Kafka topics (`agents.{agentId}.{eventType}`). No direct agent-to-agent HTTP calls.

4. **Agent Safety** — Every agent output passes through the global AI safety engine before delivery to users or other systems.

## SECTION 26 — EVENT-DRIVEN PRINCIPLES

*(Extends `docs/EVENT_ARCHITECTURE.md`)*

1. **Events are Immutable Truth** — Once an event is emitted, it is never modified. The EventStoreDB log is the single source of truth for all state transitions.

2. **Events Enable Time-Travel** — Any past system state is reconstructable from the event log. This enables: backtesting, regulatory audit, AI training, and debugging.

3. **Events Enable Agent Communication** — AI agents are event producers and consumers. The event bus is the agent communication fabric.

4. **Events Enable Collective Learning** — Anonymized, aggregated event patterns (opt-in users only) form the learning substrate for collective intelligence (Phase 3+).

## SECTION 27 — DOMAIN-DRIVEN DESIGN PRINCIPLES

*(Extends `docs/ENGINEERING_FOUNDATION.md` § DDD)*

1. **Bounded Contexts are Permanent Units** — The 49 Phase 1 bounded contexts are the primary organizational unit. As the platform expands, new contexts are added, never retrofitted.

2. **Context Isolation is Law** — Bounded contexts never share databases. Communication is exclusively through domain events (Kafka) or API calls. Direct database access across context boundaries is architecturally illegal.

3. **Ubiquitous Language Evolves** — The Ubiquitous Language (`docs/UBIQUITOUS_LANGUAGE.md`) evolves with the business. Every new domain (Phase 2: wealth management, backtesting) adds new language.

4. **Phase Expansion** — Phase 1: 49 contexts. Phase 2: +15 contexts (backtesting, paper trading, strategy, wealth, knowledge graph, collaboration). Phase 3: +25 contexts (autonomous agents, experience graph, collective intelligence, B2B, family office).

## SECTION 30 — SOLID PRINCIPLES

*(Engineering discipline — applies at all scales)*

- **S**ingle Responsibility — Every class has one reason to change. AI schools are separate classes. Repositories are separate from domain services.
- **O**pen/Closed — Open for extension (new plugins, new AI schools, new markets). Closed for modification (core domain logic).
- **L**iskov Substitution — All AI providers are interchangeable through LiteLLM. All repositories implement the same port interface.
- **I**nterface Segregation — Small, focused ports. `IMarketDataRepository` does not also handle order execution.
- **D**ependency Inversion — Domain and Application depend on abstractions (ports). Infrastructure depends on those same abstractions to implement.

## SECTION 31 — CQRS PRINCIPLES

*(Extends `docs/APPLICATION_LAYER_ARCHITECTURE.md`)*

1. **Commands and Queries are Always Separate** — `PlaceOrderCommand` and `GetPortfolioQuery` are never merged. Command handlers produce events. Query handlers read from optimized read models.

2. **Read Models are Optimized** — Each read model is optimized for its specific query, not for writes. Portfolio summary read model is different from the portfolio detail read model.

3. **Scaling Benefit** — Read/write ratio in financial systems is typically 100:1. CQRS allows independent scaling of read infrastructure without impacting write infrastructure.

---

## SECTION 32 — EVENT SOURCING READINESS

*(Extends `docs/EVENT_ARCHITECTURE.md`)*

1. **EventStoreDB is Permanent** — The event log outlives all other components. Even if the read database is corrupted, the system is fully reconstructable from the event log.

2. **Backtesting via Event Replay** — Phase 2 backtesting engine replays historical events through a strategy evaluator. This architectural capability is built into Phase 1 EventStoreDB implementation.

3. **AI Training via Event History** — The complete event history is the highest-quality AI training dataset. Every market tick, every user action, every recommendation outcome — all available for model improvement.

## SECTION 49 — DEFINITION OF PRODUCTION-GRADE

A Tradeora system is **Production-Grade** when:

1. **Zero data loss**: Every transaction is durably stored (EventStoreDB WAL + PostgreSQL WAL)
2. **Zero silent failures**: Every error is logged, alerted, traced, and actionable
3. **Regulated audit**: Every action has a tamper-proof audit trail (MinIO WORM)
4. **Defined SLAs**: 99.9%+ uptime with latency budgets met at P99 (not P50)
5. **Load validated**: System tested at 3× peak expected concurrent users
6. **Security certified**: OWASP Top 10 compliance + penetration test passed
7. **Runbooks exist**: Every failure mode has a documented recovery procedure (10 runbooks minimum)
8. **Rollback ready**: Every deployment can be rolled back in < 30 seconds
9. **On-call coverage**: At least 1 engineer is always reachable and on-call
10. **Monitoring alive**: If monitoring goes down, an alert fires (dead-man's switch)

---

## SECTION 50 — DEFINITION OF ENTERPRISE-GRADE

A Tradeora system is **Enterprise-Grade** when, in addition to Production-Grade, it satisfies:

1. **Multi-tenancy**: Isolated organizations with guaranteed data separation and independent encryption keys
2. **Compliance-ready**: Adaptable to multiple regulatory frameworks (FRA, SAMA, SEC, MIFID)
3. **Audit-grade**: Audit trail satisfies regulatory scrutiny for a minimum of 7 years
4. **SLA contracts**: Can commit to 99.99% SLA in writing to institutional clients
5. **Disaster recovery**: RTO < 4 hours, RPO < 1 hour for complete system recovery
6. **Plugin extensible**: Third parties can extend capabilities without source code access
7. **White-label ready**: Core engine separable from Tradeora branding
8. **Enterprise support**: Escalation procedures, SLA-backed support contracts
9. **Security certifications**: ISO 27001 / SOC 2 Type II (Phase 2 target)
10. **Vendor independence**: Can migrate away from any vendor within 90 days
